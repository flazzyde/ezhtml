# M1 · v0.3.0-rc.1 — WASM build of the compiler

**Target quarter:** end of April 2026
**Owner:** flazzyde
**Labels:** `roadmap`, `compiler`, `wasm`, `milestone-m1`
**Tracks under:** Q2 2026 · Compiler stream

## Goal

Ship the EZHTML compiler as a WebAssembly artifact so the browser
playground (and any future edge-function use) can compile `.ezhtml`
sources entirely client-side, with no server round-trip.

## Acceptance criteria

- [ ] `cargo test --target wasm32-unknown-unknown` passes the full
      compiler test suite.
- [ ] A new `ezhtml.wasm` npm package is published with the artifact
      and TypeScript bindings.
- [ ] The browser playground (`/playground/`) loads the WASM artifact
      directly from `node_modules` (no `fetch()` from a remote URL).
- [ ] Two of the eight starter templates (`landing`, `docs`) are
      re-recorded as snapshot tests so WASM regressions are caught in
      CI.
- [ ] A short comparison table — Rust-bundled vs. WASM flavour — lives
      in `docs/Compiler.md` so contributors know the trade-offs.

## Non-goals

- Multi-threaded WASM (we'll stay single-threaded for v0.3).
- Streaming compilation. Whole-document compile only for now.
- Server-side WASM (Cloudflare Workers, Deno Deploy) — that's a future
  milestone.

## Risks

| Risk | Mitigation |
| ---- | ---------- |
| `clap`'s derive macros emit code that doesn't compile under wasm32-unknown-unknown. | Refactor CLI argument parsing into a thin binary crate; the library stays pure. |
| Pulling in `serde_json` blows up the bundle size. | Tree-shake with `wasm-pack --release` and strip `Debug`. Budget: 600 KB gzipped. |
| Playground WASM gets out-of-sync with the compiler crate. | CI publishes both; version pins in `playground/package.json`. |

## Open questions

- Do we want to ship a thin `Composer` JS API or expose the same
  `compile(source, options) -> string` shape the crate already has?
- Should we expose a streaming variant in v0.3, or wait until the
  standalone site generator milestone?
